# Agent Instructions

## Toolchain

- This is a Unity `6000.1.6f1` project using URP, the Input System, AI Navigation, and Unity Test Framework; open the repository root in that Unity Editor version.
- There is no CI. Tests run through the Unity CLI runner in `Tools/UnityCli/`: the designer starts it on Windows with
  `start-runner.cmd`, and agents queue work with `Tools/UnityCli/unity-cli.sh exec <compile|editmode|playmode|smoke|all|sync> [testFilter]`
  (`status` shows whether the runner is alive; results land in `.unity-cli/results/`). Builds are made from the Unity
  Editor (**File > Build Settings**).
- `Packages/manifest.json` and `Packages/packages-lock.json` are the package sources of truth. Do not hand-edit generated `.sln`/`.csproj` files; they are ignored and regenerated by Unity.

## Project Structure

- Scripts live under `Assets/Scripts/`, split by system:
  - `Battle/`: the battle simulation. `Troop/` is the troop and soldier system (see `Troop/README.md` and
    `Docs/Battle/Architecture.md`), `Controller/` holds `Battle`, `Army` and `CapturePoint`, `Battle End/` the win/lose
    conditions, `Pathfinding/` the 2D NavMesh code, `Audio/` the battle sounds, `AI/` the enemy AI (see `AI/README.md`;
    it reaches troops only through the adapters in `AI/Adapters/`).
  - `Tween/`: what passes between battle and campaign: campaign characters (`CampaignCharacter`, `RosterCharacter`),
    achievements, `BattleReport`, `BattleFlow` (scene changes after a battle) and `RosterTroops` (the deployed characters' troops, handed to the
    battle's `DeploymentZone`).
  - `Campaign/`: campaign data and saving, the pre-battle tent hub, post-battle screens, cutscenes and the main menu.
  - `Misc/`: shared UI (hover tips, floating text), the input map and camera controls.
- Dependency rule: `Battle/` and `Misc/` never reference `Tween/` or `Campaign/`; the battle reports through events
  (`BattleEvents`, `Battle.Started`/`Ended`) that `Tween/` listens to. Editor tools may cross this line.
- Missions (see `Docs/Missions/README.md`): one folder per mission under `Assets/Missions/Mxx - <Title>/` with the
  mission sheet (`MissionDefinition`, code in `Scripts/Campaign/Missions/`) and `PreBattle/`, `Battle/` (scene, navmesh,
  `Map/` layer images) and `Tween/` folders. `Resources/MissionCatalog.asset` lists them in campaign order; make new
  ones with **Leveraged Wars > Missions > New Mission**.
- Battle prefabs (capture point, deployment zone, battle canvas) are in `Assets/Prefabs/Battle/`; campaign UI art and
  prefabs stay under `Assets/Campaign/`.
- `CampaignDataManager` persists across scenes and saves `campaign.json` in `Application.persistentDataPath`. Bump
  `CampaignData.CurrentSaveVersion` when the save format changes; older saves are deleted.
- Runtime-loaded assets must remain under `Assets/Resources/` and use the existing `Resources.Load` paths, especially
  `Resources/Battle Tuning/`, `Resources/Battle/Soldiers/` (soldier material and shaders), `Resources/Shaders/`,
  `Resources/Troop and Character Profiles/` and `Resources/Levels/`.
- Build Settings: the menu scenes keep indices `0` (Main menu), `1` (Battle Preparation, loaded by campaign code) and
  `2` (Post battle, loaded by `BattleFlow` on victory; defeat loads `0`). The tent loads the current mission's battle
  scene from the Mission Catalog, and Continue follows the mission's *Next Mission*. Missions' scenes follow the menus
  in catalog order: run **Leveraged Wars > Missions > Sync Build Settings** after changing them.

## Editing Rules

- Asset serialization is Force Text: scenes, prefabs and assets are YAML and can be read and diffed.
- Unity scenes, prefabs, ScriptableObjects, and other serialized assets must be edited through Unity when possible; preserve their adjacent `.meta` files and do not hand-edit YAML unless necessary.
- `Assets/Scripts/Misc/Input/PlayerInputMap.cs` is generated from `PlayerInputMap.inputactions`. Change the `.inputactions` asset and let Unity regenerate the wrapper rather than editing the generated C# directly.
- Keep changes scoped to source assets. Do not commit or rely on generated/editor directories such as `Library/`, `Temp/`, `Obj/`, `Build/`, `Builds/`, `Logs/`, `UserSettings/`, `.vs/`, or generated solution/project files.

## Docs

- `Docs/Archive/` holds out-of-date documents kept for history; do not use them as guidance.

## Specification Log

- Record every change to battle behaviour, tuning or UI, and every assumption made to fill a gap in `Docs/Battle/specifications.md`, as a new entry at the top of `Docs/Battle/SpecificationUpdate.md` (next SU-number, marked Decision or Assumption). Do not edit `specifications.md` itself unless asked.
- `Docs/Battle/AssumptionsReview.md` is the designer's checklist of every Assumption in the log. When the designer has
  marked a group (`[x]` keep, `[~]` change, `[-]` reject), fold that group into `specifications.md` when asked and note
  it in the log. Add new Assumptions to the checklist as well as to the log.

## Verification

- A task is done only when `unity-cli.sh exec compile` and `unity-cli.sh exec editmode` both pass. If a test was
  already failing before the change, say so in the session summary rather than leaving it unmentioned; do not skip or
  delete a test to make the run green without the designer's agreement. If the runner is not running, ask the designer
  to start `Tools/UnityCli/start-runner.cmd`.
- After C# or asset changes, let Unity finish importing and compiling, then check the Console for errors before running the affected scene.
- For gameplay changes, exercise the relevant mission scenes in `Assets/Missions/` (and test scenes in `Assets/Resources/Levels/`) and verify campaign transitions and save/load behavior, not only compilation.

## End of Session

Every session ends with these steps, in order:

1. Run `compile` and `editmode` through the Unity CLI runner (see Verification) and report the result.
2. Add the SU entries for the session's changes to `Docs/Battle/SpecificationUpdate.md`.
3. Update any doc whose status the session changed (for example a step in the mission workflow plan).
4. **Commit.** One commit per piece of work, never one commit for the whole session if it covered several things.
   Messages are a short imperative summary followed by the SU numbers, e.g.
   `Add mission sheets and the New Mission wizard (SU-119)`. Do not commit `Library/`, `Temp/`, `Logs/`,
   `UserSettings/` or files outside the repo's source folders. Do not push, rewrite or amend pushed commits unless asked.
5. Finish with a short summary: what changed, the commits made, the test result and anything left open.
